# Client Network Database — implementation plan

**Status:** proposal, 2026-09-15. Nothing in this document is built yet.
**Branch target:** a new branch off `develop` after `feature/ux-entitlements-v2` merges (`feature/network-db`).
**Owner:** Sharon (product), Santhosh (build/verify).

## 1. The idea in one paragraph

Some restaurants do not want their ledger in Google's cloud or on SmartDine's
Apps Script, and do not want to pay for a hosted database either. They have a
PC or a small server on the shop's Wi-Fi. This plan lets the **platform admin
configure a database that lives on the client's own network**, and lets every
SmartDine device in that shop **talk to that database directly** — no
SmartDine backend, no Apps Script, no Firestore ledger, no internet needed for
day-to-day billing. The till, the kitchen screen and the waiter pads share one
ledger over the LAN. Several database engines are supported through one
storage abstraction, so the client uses whatever they already run.

This is a **fourth storage mode**, `CLIENT_NETWORK_DB`, next to
`PURE_OFFLINE`, `CLOUD_SYNC` and `CLIENTS_OWN_SHEETS`. It follows every rule
in `FEATURE_MASTER_PLAN.md`: one resolver, off-means-absent, the storage-mode
change flow, billing survives everything.

## 2. How this relates to earlier decisions

`SUPABASE_DATA_STORE_DESIGN.md` (9 Sep) decided to put a client database
*behind Apps Script* so that "no database credential ever reaches a tablet".
This plan is the deliberate opposite for a different customer: a shop that
wants **no third party in the path at all**. Both can coexist — Supabase
behind `Code.gs` is still the right answer for a hosted database; this is the
answer for a LAN database. The consequence is stated plainly in §8: the
database credential does live on the device, encrypted, and the design treats
that as the central risk rather than pretending it away.

## 3. Scope

In scope:

- A new storage mode configured per tenant by the platform admin (engine, host,
  port, database, schema, TLS), with the secret entered by the store owner on
  their device, never stored in Firestore.
- One ledger abstraction (`LedgerStore`) with three implementations: Hive
  (offline), Webhook (today's Apps Script / Sheets path), SQL (this plan).
- SQL dialects for **PostgreSQL** and **MySQL / MariaDB** first; **Microsoft
  SQL Server** as an optional later dialect. SQLite over a network share is
  explicitly *not* supported (file locking over SMB corrupts databases).
- Schema DDL and migrations per engine, generated by the app and either run by
  the client's IT or by the app itself when the connection has the rights.
- Multi-device on the LAN (KDS, waiter pads, second till) without internet.
- Migration into and out of this mode through the existing
  `StorageMigrationService` (consent → provision → migrate → verify → flip).
- Health and resumption when the LAN or the database host is down.

Out of scope (for this plan): the guest web menu / QR ordering on a LAN-only
tenant (needs internet and a public endpoint — those stay under `cloudSync`
and can be added as a hybrid later, see §7.3); replication or backups of the
client's database (their IT's job — we give them the commands); web/browser
builds of the app (raw sockets are not available in Flutter web).

## 4. Supported engines and drivers

| Engine | Dart driver | Status | Notes |
|---|---|---|---|
| PostgreSQL 13+ | `postgres` ^3.x (pure Dart) | Phase N2 | Best driver; TLS, prepared statements, `ON CONFLICT`, `FOR UPDATE`. First target. |
| MySQL 8 / MariaDB 10.5+ | `mysql_client` ^0.12 (pure Dart) | Phase N3 | `INSERT … ON DUPLICATE KEY UPDATE`, `SELECT … FOR UPDATE`. Requires `caching_sha2_password` or `mysql_native_password`. |
| Microsoft SQL Server 2017+ | `mssql_connection` (Android JDBC bridge) | Optional N6 | Android only today; iOS/desktop would need a different driver. Offer only when a client asks. |
| SQLite on a shared folder | — | Never | Not safe over a network. The offline mode already covers single-device SQLite-class needs via Hive. |

Platform support: Android and iOS (native sockets), Windows/macOS desktop
builds. **Not Flutter web.** The app hides the mode's device setup on web.

Pin every driver to an exact major and add them in the dependency-upgrade
tranche we already agreed, so a driver bump never lands in the same commit as
a behaviour change.

## 5. Architecture

### 5.1 One ledger surface

Today writes go to Hive and, on cloud tenants, to Apps Script through the
outbox; reads come from Hive with a cloud pull (`GET_ORDERS` / `GET_DELTA`).
The new layer names what is already there:

```dart
abstract class LedgerStore {
  Future<void> upsertOrder(KotOrder o, {required String clientRequestId});
  Future<void> updateOrderStatus(...);            // compare-and-set on rev
  Future<void> recordPayment(...);
  Future<void> setTableStatus(...);
  Future<List<KotOrder>> readOrdersSince(int rev, {int limit});
  Future<int> currentRev();
  Future<LedgerHealth> ping();
  Future<void> ensureSchema();                    // no-op for Hive/Webhook
}
```

Implementations:

- `HiveLedgerStore` — what `LocalStore` does today, wrapped. Always present;
  every other store writes *through* it first (local-first never changes).
- `WebhookLedgerStore` — the Apps Script calls the outbox already makes
  (`SAVE_BILL`, `UPDATE_ORDER_STATUS`, `RECORD_PAYMENT`, `SET_TABLE_STATUS`,
  `CLEAR_TABLE`, `GET_DELTA`). No behaviour change; it is a rename.
- `SqlLedgerStore` — this plan. One class, one `SqlDialect` per engine
  (`PostgresDialect`, `MySqlDialect`, later `MsSqlDialect`) that owns the
  connection, the DDL text and the handful of statements that differ (upsert,
  row lock, last-insert semantics, parameter placeholders).

`LedgerStore.forTenant(entitlements)` picks the implementation from the
storage mode. The **outbox does not change shape**: `Outbox.drain()` hands
each `OutboxOp` to `store.apply(op)` instead of switching on action names
inline. Idempotency stays `clientRequestId`.

### 5.2 Where the configuration lives

Non-secret, set by the platform admin in the features console
(`organizations/{orgId}.networkDb`):

```json
{
  "engine": "postgres",            // postgres | mysql | mssql
  "host": "192.168.1.20",          // IP or LAN hostname (mDNS ok: pos-db.local)
  "port": 5432,
  "database": "smartdine",
  "schema": "public",              // postgres only
  "tls": "prefer",                 // disable | prefer | require
  "schemaVersion": 0,              // last version the app confirmed on the DB
  "lastCheck": { "at": "...", "ok": true, "byDevice": "…", "detail": "…" }
}
```

Secret, **never in Firestore, never in audit logs**: the database username
and password. Entered once by the **store owner on their device** in the
network-database setup screen. Stored in Hive encrypted with
`SaasCryptoService` under a key kept in the platform keystore
(`flutter_secure_storage`). Other devices in the shop get it one of two ways,
both owner-initiated: the owner shows a **join QR** (the encrypted credential
blob + host, valid 10 minutes, generated on the LAN), or the owner types it in
on that device. The platform admin never sees or holds the password.

Two database roles are recommended in the DDL pack: `smartdine_app` (DML on
the ledger tables only) and `smartdine_admin` (DDL, used once for setup). The
app runs as `smartdine_app`; `ensureSchema()` only *checks* the version unless
the connection happens to have DDL rights and the owner presses "Set up
schema".

### 5.3 Schema

Same model as the Supabase design (so a later move between the two is a data
copy, not a redesign), typed for each engine:

`orders`, `order_items`, `payments`, `sessions`, `tables`, `reservations`,
`dishes`, `expenses`, `alerts`, `audit`, `idempotency`, `counters`,
`outlet_rev`, `schema_migrations`.

Rules: money as `BIGINT` paise (`grand_total_p`, `amount_p`), never floats;
`kitchen_status` and `payment_status` as separate columns (X-17); `rev BIGINT
NOT NULL` on every row with index `(outlet_id, rev)`; `idempotency` has a
unique index `(outlet_id, client_request_id)`; timestamps stored as UTC.

Engine differences the dialect hides:

| Concern | PostgreSQL | MySQL/MariaDB | SQL Server |
|---|---|---|---|
| Upsert | `INSERT … ON CONFLICT (…) DO UPDATE` | `INSERT … ON DUPLICATE KEY UPDATE` | `MERGE` |
| Row lock for rev bump | `SELECT … FOR UPDATE` | `SELECT … FOR UPDATE` | `WITH (UPDLOCK, ROWLOCK)` |
| JSON column (items snapshot) | `JSONB` | `JSON` | `NVARCHAR(MAX)` |
| Boolean | `BOOLEAN` | `TINYINT(1)` | `BIT` |
| Placeholders | `@name` (driver) | `:name` (driver) | `@name` |
| Schema namespace | yes | database = schema | yes |

`schema_migrations(version INT, applied_at)` gates the app: a device whose
app expects version *n* but finds *m < n* shows "the store database needs an
update — owner to run Set up schema", and keeps billing locally (rule 7).

### 5.4 Concurrency without a single writer

Apps Script gave us a single writer and `LockService`. A LAN database gives us
transactions instead, and the store uses them the same way:

- Every write runs in one transaction: lock the tenant's `outlet_rev` row
  (`FOR UPDATE`), insert the idempotency key (`ON CONFLICT DO NOTHING` — a
  no-op means "already applied", return success), write the rows with
  `rev = next`, bump `outlet_rev`, commit.
- Status changes are compare-and-set: `UPDATE orders SET kitchen_status=?,
  rev=? WHERE id=? AND rev=?`; zero rows updated means someone else moved it,
  the client re-reads and re-applies or shows the conflict (same as the
  webhook's `rev` semantics today).
- Reads are `WHERE outlet_id=? AND rev>? ORDER BY rev LIMIT ?` — the existing
  `SyncEngine` delta poll, pointed at SQL.

No server-side validation exists in this mode; all devices run the same app
version and the schema version gate keeps them honest. That trade is the
price of "no backend" and is written down here so nobody is surprised.

### 5.5 Health, outage and resumption

`LedgerHealth { reachable, latencyMs, schemaVersion, lastOkAt }` is polled
every 15 s by the `SyncEngine` when this mode is active (one poller, owned by
the mode, idle in every other mode — rule 4). When the database is
unreachable:

- Till keeps billing; writes queue in the outbox exactly as they do for a
  cloud tenant with Wi-Fi down.
- KDS and waiter pad show a one-line "store database unreachable since 14:02
  — showing what this device last saw" banner; no exceptions, no spinners.
- When it comes back the outbox drains in order, then the delta poll catches
  up. Nothing is lost, nothing is duplicated (idempotency).

Internet is irrelevant to all of this. `CloudGate` keeps meaning *internet*
and stays **closed** for a `CLIENT_NETWORK_DB` tenant unless the hybrid flag
in §7.3 is on; database reachability is a separate signal.

## 6. Platform-admin console

In the existing features console (`admin_features_view.dart`), the storage
section gains a fourth option, **Client network database**, with a small
form: engine, host, port, database, schema (Postgres only), TLS. The admin
cannot test the connection — the database is on the client's LAN, not
reachable from the console — so the form shows the **last check reported by a
device** (`networkDb.lastCheck`) and a "Generate schema pack" button that
downloads the DDL for the chosen engine plus a one-page setup note for the
client's IT (create database, create the two roles, run the DDL, open the port
on the LAN only, give the PC a fixed IP or hostname).

Choosing the mode for an existing tenant writes `pendingStorageChange` exactly
as the other modes do. The tenant editor's dropdown gets the same fourth item.
Hard constraints for this mode in the resolver: devices follow the licence (it
is multi-device by design); **outlets are pinned to 1** — a LAN database serves
one venue, cannot be reached by other branches or by the platform admin, so the
option is hidden when `multiOutlet` is on or the licence has more than one
outlet, with the notice "Client network database connects over the venue's
LAN and is available for single-outlet stores only"; cloud/internet keys off
unless hybrid.

## 7. Entitlements

### 7.1 Catalogue change

`FeatureNeed` gains one value:

- `none` — works on one device with local storage.
- `sharedLedger` — needs more than one device to see the same orders (KDS,
  waiter ordering). Satisfied by `CLOUD_SYNC`, `CLIENTS_OWN_SHEETS` **and**
  `CLIENT_NETWORK_DB`. Today these are tagged `secondDevice`; rename.
- `cloud` — needs the internet (analytics-cloud, online menu, QR ordering,
  online ordering, e-mail receipts, multi-outlet).

`kdsEnabled` and `waiterOrdering` move from `secondDevice` to `sharedLedger`;
nothing else changes. Their `dependsOn` stays.

### 7.2 Resolver

`StorageModes.clientNetworkDb = 'CLIENT_NETWORK_DB'`, `isOffline()` stays
`PURE_OFFLINE` only, new `hasSharedLedger(mode)` true for the three
multi-device modes. Hard constraints:

| Mode | maxDevices | `sharedLedger` keys | `cloud` keys |
|---|---|---|---|
| PURE_OFFLINE | 1 | off | off |
| CLIENT_NETWORK_DB | licence | licence | off (hybrid: licence) — **maxOutlets = 1**: one LAN is one venue; the mode is hidden when `multiOutlet` is on or outlets > 1 |
| CLOUD_SYNC / CLIENTS_OWN_SHEETS | licence | licence | licence |

`cloudSync` itself is a `cloud` key and is **off** for a LAN tenant, which is
what makes every existing `featureOn(cloudSync)` gate (Sheets sync, Firestore
publish, Refresh buttons, KOT sound over the internet) fall silent correctly.
KOT sound and the KDS pollers need a second gate, `featureOn(kdsEnabled)` /
`hasSharedLedger`, which already exists for KDS and is added for the sound
toggle.

### 7.3 Hybrid (later, optional)

`organizations.networkDb.internetAddOns = true` lets a LAN tenant that also
has internet turn on `cloud` keys (online menu, QR). The ledger stays on the
LAN; only the public menu and incoming web orders touch Firestore/Apps Script,
and web orders arrive via the existing `GET_ORDERS` pull into the LAN ledger.
Not in the first build; noted so the resolver leaves room for it.

## 8. Security posture — stated plainly

- The database password is on every device in the shop, encrypted at rest
  with a key in the OS keystore. A rooted device with the app's key can
  recover it. Mitigation: the `smartdine_app` role can only touch the ledger
  tables; the database listens on the LAN only; the join QR expires.
- TLS: `require` is forced when the host is not a private address
  (RFC 1918 / `.local`); `prefer` is the default on the LAN.
- Nothing about the connection is logged or audited beyond engine/host/port.
- The client owns backups. The schema pack ships `pg_dump` / `mysqldump`
  one-liners and a Windows Task Scheduler example; the in-app encrypted
  backup (`backupRestore`) still covers this device's local copy.
- The platform admin never holds the credential and cannot reach the ledger.
  That is a feature for this customer, and a support limitation to explain
  up front: SmartDine cannot see their data to help debug it.

## 9. Owner-side setup and migration

New screen `NetworkDatabaseSetupScreen` (owner only), reached from the
migration gate when the pending target is `CLIENT_NETWORK_DB`, and from
Settings → Store database afterwards:

1. Shows the admin's engine/host/port/database read-only.
2. Owner enters username and password → **Test connection** (latency,
   server version, schema version).
3. If the schema is missing or old: "Set up schema" (runs the DDL when the
   role allows it) or "Show the SQL for your IT".
4. **Join code** — generates the 10-minute QR for other devices.

`StorageMigrationService` gains a `SqlTarget` so the four steps map onto this
mode with no new flow: consent = credentials + successful test; provision =
schema at the expected version; migrate = every local bill through the outbox
to SQL (menu, tables, expenses ride along); verify = ids present in SQL ⊇ local
ids; flip. Reverse (LAN → offline) pulls the SQL ledger into Hive. Cross
(cloud → LAN) pulls from the webhook, pushes to SQL, verifies against SQL.

## 11. Acceptance (fresh tenant on `CLIENT_NETWORK_DB`)

- Wi-Fi on, internet **off**: till bills, KDS receives the KOT within 5 s,
  waiter pad sees the table, Z-report runs, history shows every bill. Zero
  internet requests other than the sign-in licence check.
- Pull the database PC's network cable: till keeps billing; KDS shows the
  banner; nothing crashes. Plug it back: queue drains in order, KDS catches
  up, no duplicate rows (`SELECT count(*)` vs local).
- Two tills settle different bills at the same second: both land, `rev`
  strictly increasing, idempotency table has exactly one row per request.
- Old app version against a newer schema: gate message, billing continues.
- Admin cancels a pending change mid-way: tenant returns to the old mode,
  local data intact.
- Console never displays, logs or stores the password; `audit_logs` carries
  engine/host only.
